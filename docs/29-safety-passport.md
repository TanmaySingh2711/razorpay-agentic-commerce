# 29 — Agentic Purchase Safety Passport

_Objective 20. Additive, presentation-layer, zero schema change._

## What it is

A compact panel on the transaction page that answers one question in a few
seconds: **why was this AI-assisted purchase safe?**

It sits between the status cards and the audit timeline and reports, for the
transaction in front of the reader:

- what the assistant was allowed to do, and what it was not;
- which financial facts were decided by deterministic server code;
- whether spending policy was evaluated, and what it returned;
- whether a human approval was required, and whether one was granted;
- whether stock was held, and whether it was committed;
- the browser callback verification and the provider capture, **separately**;
- whether retries were bounded, and how each attempt ended;
- whether a redelivered provider event was deduplicated;
- the transaction's final state.

## What it is not

It is **not a replacement for the audit timeline**. The timeline below it is
still the complete chronological evidence, unchanged. The passport is the
thirty-second summary for a reviewer who will not read forty rows, and it says
nothing the trail does not already contain.

It is also not a badge. A blocked, failed, cancelled or expired purchase gets a
passport too, and it reports what actually happened rather than a success
narrative — the subtitle itself changes to _"What this AI-assisted purchase was
allowed to do, and where it stopped."_

## It is deterministic, and no model writes any part of it

Every claim comes from persisted, server-derived records:

| Claim                     | Derived from                                                                                                                         |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| AI selection bounded      | `AuditEvent` — `product_verified` / `product_selection_rejected`                                                                     |
| Price verified            | `PurchaseQuote` rows (status, total, currency)                                                                                       |
| Spending policy           | The recorded `policy_evaluated` decision and reason code                                                                             |
| Human approval            | `ApprovalRequest` rows plus the `approval_granted` audit count                                                                       |
| Inventory reservation     | `InventoryReservation` rows                                                                                                          |
| Payment amount            | Every `PaymentAttempt` amount, checked against amounts this transaction quoted                                                       |
| Callback verification     | `AuditEvent` — `payment_verified` / `payment_callback_rejected`                                                                      |
| Provider capture          | `AuditEvent` — `payment_captured`, and `PaymentAttempt.status`                                                                       |
| Inventory committed       | `AuditEvent` — `inventory_committed`, plus committed reservation rows                                                                |
| Retry / re-quote / replay | `PaymentAttempt` rows, `quote_reissued`, `inventory_reservation_requoted`, `webhook_duplicate`, and the server-computed retry status |
| Final state               | `Transaction.status`, via the state machine's own history                                                                            |

**No Gemini call is made, and none can be.** The builder is a pure function over
a fact type that carries persisted values only — there is no field a model
output could be placed in. This matters because a sentence a language model
writes is a plausible sentence, not evidence, and a safety summary generated by
a model would be exactly the artefact this system spends seventeen states
avoiding: a confident claim with nothing underneath it.

## The rule every branch obeys

A positive claim requires evidence for **that specific claim**:

- "Captured" is never inferred from a verified callback. `PAYMENT_VERIFIED`
  proves the browser's message was authentic; only a capture record is money.
- "Committed" is never inferred from a capture. Stock leaves the warehouse only
  against a confirmed capture, and the passport waits for the commit record.
- **"Exactly once" is never inferred from a single current row.** One committed
  reservation shows the present; "once" is a claim about history, so it also
  requires exactly one `inventory_committed` audit record. With any other
  combination the passport says "Committed" and prints the counts.
- "Approved once" likewise requires one approved row _and_ one
  `approval_granted` record.
- Where the evidence is absent the status is `NOT_REACHED`, drawn neutral. A
  step that has not happened is a fact, not an achievement.

Language is factual throughout — verified, bounded, authorized, captured,
committed, deduplicated. The words "secure", "guaranteed", "fraud-proof" and
"100% safe" appear nowhere, and a test asserts they never will.

## Where the code lives

| Piece                                   | File                                             |
| --------------------------------------- | ------------------------------------------------ |
| Pure builder, statuses, tones, evidence | `src/domain/safety/passport.ts`                  |
| Read-only row reader and fact assembly  | `src/services/safety/passport-service.ts`        |
| Wiring into the page's single read      | `src/services/transaction/overview-service.ts`   |
| Rendering                               | `src/components/transaction/safety-passport.tsx` |

The passport is built inside `loadTransactionOverview`, alongside everything
else the page reads, and its extra queries run in the same parallel batch — so
it costs no additional round trip. Like the rest of that value it is **strictly
read-only**: rendering a page can never move a transaction.

## No schema change

Deliberately zero migrations. The passport is a _view_ of records Objectives
1–19 already made authoritative. A new table would be a second place the truth
lives, and the first time the two disagreed the passport would be worse than
useless — it would be confidently wrong.

## Tests

- `tests/safety-passport.test.ts` — the pure mapping from records to claims,
  including every negative case above.
- `tests/db/safety-passport.test.ts` — the same claims against real PostgreSQL,
  driven through the genuine boundaries (product decision, policy, approval,
  reservation, payment order, checkout, webhook). The fixtures fabricate no
  audit events: the evidence the passport counts is what the services wrote
  while doing ordinary work.
